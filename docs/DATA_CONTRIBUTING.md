# Data contribution guide

Thank you for contributing to the Indian Metro Network Tracker! This document outlines how data corrections are handled, how to report errors, and how to submit code/data changes.

---

## 1. Reporting an issue

If you spot an error while browsing the map (e.g. an incorrect station name, opening date, line alignment, or status):

1. Click on the station or line segment on the map to open the detail panel.
2. Scroll to the bottom of the panel and click the **"Report an issue"** button.
3. This opens a prefilled GitHub issue with the diagnostic details (Feature ID, city, timestamps, displayed values, and map permalink).
4. Provide the **Source Link** (a link to an official transit operator press release, operational website, or government gazette).
5. Submit the issue! A maintainer will review the source and apply the override.

---

## 2. Direct data contributions

If you would like to submit a data correction yourself, follow the workflow below.

### Absolute Rule: Never Hand-Edit Generated Files
Do **not** edit generated files in `data/`:
- `data/cities.json`
- `data/lines.json`
- `data/segments.geojson`
- `data/stations.geojson`

These files are programmatically generated by the build pipeline. Any direct modifications will be overwritten on the next pipeline run.

### The Single Source for Corrections: Overrides Files
All human corrections and manual metadata adjustments must be placed in:
```
data/overrides/<city-id>.json
```
For example: `data/overrides/delhi.json`, `data/overrides/mumbai.json`, `data/overrides/chennai.json`.

---

## 3. Override File Structure

Each city override file follows the structure:

```json
{
  "city_id": "delhi",
  "lines": [ ... ],
  "segments": [ ... ],
  "stations": [ ... ]
}
```

### Station Override Example
```json
{
  "station_id": "del-kashmere-gate",
  "name": "Kashmere Gate",
  "name_hi": "कश्मीरी गेट",
  "opened_on": "2006-11-11",
  "is_interchange": true,
  "references": [
    "https://www.delhimetrorail.com/network_map"
  ],
  "last_verified": "2026-03-15"
}
```

### Segment Override Example
```json
{
  "segment_id": "del-red-seg-01",
  "inaugurated_on": "2002-12-24",
  "operator": "Delhi Metro Rail Corporation (DMRC)",
  "references": [
    "https://www.delhimetrorail.com/corporate"
  ],
  "last_verified": "2026-03-15"
}
```

## 4. Citation and Verification Rules

Every value sourced outside OpenStreetMap (OSM) must adhere to our [Data Standards](DATA-STANDARDS.md):

1. **Source Hierarchy**:
   - Tier 1: Official transit operator website, annual reports, fare charts, network maps.
   - Tier 2: Government gazette notifications, Ministry of Housing and Urban Affairs (MoHUA), Detailed Project Reports (DPR).
   - Tier 3: Reputable mainstream journalism (The Hindu, Indian Express, Times of India, etc.).
   - **Never acceptable**: Wikipedia as a sole source, unverified social media posts, or personal speculation.
2. **Mandatory Citations**:
   - Any overridden or added field requires a valid HTTP/HTTPS URL in the `references` array.
   - Set `last_verified` to the date you personally validated the source (format `YYYY-MM-DD`). Do not let machines set this date automatically.
3. **No Guessing**:
   - If an operational date or property is unknown, keep it `null`. Never invent dates or facts.

## 5. Local verification workflow

After editing an override file in `data/overrides/`:

1. **Rebuild the dataset**:
   ```bash
   npm run pipeline:build
   ```
2. **Validate schemas & relational constraints**:
   ```bash
   npm run validate:data
   ```
3. **Run data audit consistency report**:
   ```bash
   npm run audit:data
   ```
   Ensure zero errors are reported for the city.
4. **Run the test suite**:
   ```bash
   npm test
   ```
5. Run `npm run lint`, `npm run typecheck`, `npm test`, and relevant Playwright checks.
6. Submit a pull request detailing the changes, generated-data rebuild, audit result, and sources.

## 6. Geometry and current code conventions

- Use `lib/station-style.ts` for station marker geometry and colours.
- Use `lib/filter-utils.ts` for shared station and segment visibility rules.
- `exact` is reserved for surveyed or construction-stage geometry supported by evidence.
- `schematic` is used for explicitly labelled station-derived or hand-drawn alignments where exact route geometry is unavailable.
- Preserve the `del-silver` URL/search alias for old Silver Line links.
- Never hand-edit generated data. Fix overrides or pipeline rules, rebuild, and audit.
